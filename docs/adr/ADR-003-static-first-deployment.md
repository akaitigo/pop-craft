# ADR-003: 固定費0円のブラウザ完結構成へ移行する

**日付**: 2026-07-20
**ステータス**: 承認済み
**決定者**: プロジェクトオーナー、実装担当

## コンテキスト

POP-CraftのMVPは、固定された15テンプレートの取得とPDF生成のためにGo APIへ依存している。APIを本番公開すると、サーバー費用、無料枠超過、監視、障害対応、CORS、rate limit等の運用が必要になる。一方、主要な編集と描画は既にCanvas APIでブラウザ内実行でき、認証・DB・ユーザー間共有は初期の需要検証に不要である。

ADR-001では固定テンプレートをGo構造体で保持すると決定したが、これはGo APIを本番実行する前提だった。本ADRは、本番サイトのテンプレート保存先に関するADR-001の決定を置き換える。

## 決定要因

- 最初の売上までホスティング固定費を0円にする
- 無料枠超過による予期しない請求を避ける
- サーバー、DB、認証、CORS、バックアップの運用を持たない
- 商品情報や生成内容を外部サーバーへ送信しない
- 既存のCanvasプレビューとブラウザ印刷を再利用する
- 必要になった場合にAPIを再導入できる移行余地を残す

## 検討した選択肢

### 選択肢A: Go APIをCloud Runへ配置する

**メリット**: 既存実装を維持でき、サーバー側PDF生成の出力を統制しやすい。

**デメリット**: 無料枠でも外向き通信、build、artifact、logging等に課金余地があり、監視とセキュリティ運用が必要になる。

### 選択肢B: Cloudflare Workers APIへ移植する

**メリット**: 静的配信と同一基盤に置け、Freeプランは上限到達時に停止する。

**デメリット**: Go PDF実装を再利用できず、固定データの取得だけにWorkerを置くのは不要な複雑性になる。

### 選択肢C: Next.jsを静的exportし、ブラウザ内で完結する

**メリット**: サーバー固定費とAPI攻撃面をなくし、Static Assetsで配信できる。入力データを端末外へ送信しない。

**デメリット**: 印刷・PDF保存の品質がブラウザとプリンタに依存する。テンプレート更新には再buildが必要になる。

## 決定

**選択肢C**を選択した。固定テンプレートを型付きTypeScriptデータとしてbundleし、公開UIからGo API依存を除去する。PDFはブラウザの印刷画面から保存する。Next.jsは`output: "export"`で静的成果物を生成する。

Go backendは当面、履歴と比較検証のためリポジトリに残すが、本番サイトの実行時依存にはしない。

## 結果

**ポジティブ**:

- 静的ホスティングだけで主要操作が完結する
- サーバー費用、API障害、CORS、認証情報漏えいのリスクがなくなる
- 入力した商品情報を外部へ送信しない
- 無料デモの需要検証を最小構成で開始できる

**ネガティブ/トレードオフ**:

- サーバー生成PDFと同一の出力は提供しない
- 用紙実寸、フォント、改ページはブラウザ別の検証が必要になる
- backendとfrontendのテンプレートが並存する間は不整合が起こり得る

**リスク**:

- Webフォント未読込時に代替フォントでCanvasが描画される
- ブラウザ印刷設定によって余白や倍率が変わる
- 将来、履歴共有や有料アカウントが必要になるとAPI再導入が必要になる

## 実装メモ

1. テンプレートを`frontend/src/data/templates.ts`へ移す
2. API clientとサーバーPDFの公開UIを削除する
3. 印刷画面からPDF保存できることをUIで案内する
4. Next.jsを静的exportへ変更し、`frontend/out/`を生成する
5. READMEとPRDをブラウザ完結構成へ更新する
6. 後続IssueでWebフォント読込、用紙実寸、CSP、Cloudflare設定を検証する

ロールバックする場合は、Git履歴からAPI clientを戻すだけでは本番公開しない。認証、rate limit、費用上限、監視、CORS、データ取扱いを設計した別IssueとADRを先に承認する。
